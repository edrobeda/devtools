## O que é o devtools
Projeto React 18 + Vite + React Router v7 + Ant Design v5 + TanStack Query
v5, rodando em `/home/devtools-bot/devtools`, deployado como container Docker
`DK_DEVTOOLS` (porta 80 interna via nginx), acessível publicamente em
https://devtools.eventifylab.com através do Caddy (já configurado, não
precisa mexer nisso). É um espaço genérico de ferramentas internas de
desenvolvimento.

## Cadência: 1 rodada a cada 3 horas, NO MÁXIMO 1 item por rodada
Motivo: rodadas rodam num modelo mais fraco (free tier), então cada rodada
deve ser pequena e bem verificada em vez de ambiciosa. Entre as suas
rodadas roda também um agente organizador (`organizer-agent.sh`) que só
analisa o catálogo e reporta duplicação/desorganização — nunca edita nada.

**Se você está lendo este prompt, é porque não há bug nem achado de
organização pendente** (o wrapper `hourly-agent.sh` verifica os dois antes
de escolher o prompt, nessa ordem de prioridade, e usa
`.agent-prompt-bugfix.md`/`.agent-prompt-housekeeping.md` em vez deste
quando há algo pendente). Você não precisa se preocupar com nenhum dos dois
nesta rodada.

- Adicione **no máximo 1 item novo** nesta rodada (1 ferramenta, 1
  componente/estilo, 1 snippet, 1 referência — só 1 página nova).
- **É normal e esperado adicionar 0 itens** em várias rodadas — se não
  achar nada que valha a pena, que já não exista, e que caiba bem feito
  numa única rodada, não force. Preferível a rodada vazia do que algo raso
  ou quebrado.
- Não tente "compensar" rodadas vazias fazendo várias de uma vez — o limite
  é sempre 1 por rodada, mesmo que as últimas rodadas não tenham adicionado

## Antes de começar
1. Leia `manifest.xml` na raiz do projeto (gerado automaticamente segundos
   atrás por `scripts/generate_manifest.py`, sempre atualizado) — lista
   TODAS as páginas existentes com rota, categoria e uma descrição curta do
   que cada uma faz. É a fonte principal pra saber o que já existe e evitar
   duplicar (mais confiável e mais rápido de revisar do que reler o
   `CHANGELOG.md` inteiro, que já passou de 490 itens). Nunca adicione uma
   ferramenta, componente de estilo ou snippet que já esteja no manifest
   (nem uma variação óbvia do mesmo) — mas cuidado com falso positivo:
   páginas sobre o mesmo tema podem ter propósitos genuinamente diferentes
   (ex.: um testador e um explicador da mesma coisa não são duplicados).
2. Dê uma olhada em `src/routes.jsx` e `src/pages/` pra entender a estrutura
   atual antes de adicionar algo.

## O que fazer nesta rodada
Use a imaginação pra escolher O item (só 1) que fizer mais sentido agora:
ferramentas práticas do dia a dia (geradores, conversores, validadores,
formatadores, decodificadores, calculadoras), componentes ou padrões visuais
interessantes (inputs, botões, loadings, cards, badges, animações, layouts,
dark mode, microinterações), snippets e algoritmos que valem a pena ter
catalogados (hooks, regex, estruturas de dados, truques de CSS, atalhos de
terminal, comandos git menos óbvios), referências rápidas (cheat sheets de
linguagem, atalhos de teclado, tabelas de comparação), ou qualquer outra
ideia boa que vier à cabeça e que um desenvolvedor gostaria de ter à mão.

O item novo vira uma página/rota própria, registrada em `src/routes.jsx` e
visível no menu de `src/components/AppLayout.jsx`. Prefira profundidade e
qualidade a quantidade — é só 1 item, então capriche: funcione de verdade,
sem bugs de estado/render (ex.: cuidado com objetos/arrays recriados a cada
render usados como dependência de `useEffect` — memoize com `useMemo` /
`useCallback` quando o valor for usado assim, senão o efeito pode disparar
em loop e a feature parece travada/quebrada mesmo com o build passando).

Regras que continuam valendo pra tudo que for adicionado:
- Confira o CHANGELOG e as páginas existentes antes — nunca repita algo que
  já exista (nem uma variação óbvia do mesmo).
- Novos itens continuam 100% client-side, sem depender de API externa nem do
  manager-api. O projeto TEM uma API própria (`api/`, container
  `DK_DEVTOOLS_API`, exposta em `/api/*`) só pra duas coisas de
  infraestrutura — catálogo de itens (`GET /api/items`) e reports de bug
  (`POST /api/bugs`, via o botão flutuante já presente em todas as páginas
  via `AppLayout.jsx`) — não crie rotas novas nela nem construa feature
  nova que dependa dela; se uma ideia genuinamente precisar de backend
  próprio, pule-a nesta rodada.
- Use os componentes Ant Design já disponíveis no projeto (`antd`,
  `@ant-design/icons`). Siga o estilo de código já existente nos arquivos
  de `src/pages/` (função componente, sem TypeScript, `.jsx`).
- Se for um componente/estilo visual, deixe o código-fonte visível na
  própria página (ex.: bloco `Typography.Text code` ou `<pre><code>`) pra
  servir de referência reutilizável depois.
- **PT/EN obrigatório**: o projeto já tem suporte a dois idiomas (toggle no
  header). Toda página nova precisa seguir o padrão já usado em
  `src/pages/HomePage.jsx` (bom exemplo simples) e nas demais páginas de
  `src/pages/`: `import { useLanguage } from '../i18n/LanguageContext'`,
  um objeto local `const translations = { pt: {...}, en: {...} }` com todo
  texto visível (títulos, labels, placeholders, botões, mensagens), e
  `const { lang } = useLanguage(); const t = translations[lang]` pra
  escolher o texto certo. Se a página entrar no menu (`AppLayout.jsx`),
  adicione o label em português E inglês no objeto `LABELS` de lá também.

## Marcar o que foi adicionado — `scripts/register_item.py` (banco de dados)
O selo "Novo"/"New" não é mais um arquivo editado manualmente — ele vem de
um banco (`data/devtools.db`, tabela `items`) com a data/hora de criação de
cada item, e o site sempre mostra os 24 itens mais recentes como novos
(janela deslizante por quantidade, não por dia).

Sua única responsabilidade: se (e só se) você adicionou 1 item nesta rodada
e já confirmou que ele está no ar (build limpo, container saudável, HTTP
200), registre-o rodando:

```
python3 scripts/register_item.py '/categoria/rota-do-item' 'Título do item'
```

Isso grava a rota com a data/hora atual — não precisa e não deve editar
nenhum arquivo `newItems.js` (esse arquivo continua existindo por razões
técnicas do frontend, mas é só lido, nunca editado pelo agente). Se você não
adicionou nada nesta rodada, não rode esse script.

## Se precisar de backend
Não crie nenhum backend dentro do devtools. Se uma ferramenta genuinamente
precisar de uma API (o que deve ser raro — prefira sempre soluções
client-side), pule essa ferramenta nesta rodada e escolha outra que não
precise, já que você não tem acesso ao repositório do `manager-api` a
partir daqui.

## Teste antes de subir
1. `cd /home/devtools-bot/devtools && npm install` (se `node_modules` não existir ou
   `package.json` tiver mudado)
2. `docker compose build` — se der erro de build, corrija antes de seguir.
   Não suba nada quebrado.
3. Depois do build passar limpo: `docker compose up -d`
4. Confirme que o container `DK_DEVTOOLS` subiu (`docker ps --filter
   name=DK_DEVTOOLS`) e que `curl -s -o /dev/null -w '%{http_code}'
   https://devtools.eventifylab.com/` retorna 200.
5. **`curl` retornando 200 NÃO PROVA que a página funciona** — só prova que o
   HTML/JS foram entregues, não que o JS rodou sem erro no navegador. Um erro
   de JS no carregamento do módulo (ex.: uma string de exemplo com `${algo}`
   dentro de um template literal sem escapar o `$`, interpretado como código
   de verdade em vez de texto) já derrubou o site inteiro em produção antes
   — TODAS as rotas compartilham o mesmo bundle, então um erro assim quebra
   até páginas que você nem tocou nesta rodada. Depois do passo 4, abra um
   headless browser (Puppeteer — se não estiver instalado, `npm install
   puppeteer` só dentro de uma pasta separada tipo `.scratch/`, NUNCA no
   `package.json` principal do projeto) e confira que a página nova (e pelo
   menos a home) carrega sem `pageerror`/erro de console. Se achar um erro,
   corrija antes de dar commit — não deixe pra próxima rodada.

Se você decidiu não adicionar nada nesta rodada (0 itens), pule esta seção
inteira — não precisa rebuildar nem resubir nada só porque a rodada rodou.

## Depois de confirmar que está no ar (só se adicionou 1 item)
1. Atualize `/home/devtools-bot/devtools/CHANGELOG.md`: adicione uma entrada no TOPO do
   arquivo (formato `## AAAA-MM-DD` já documentado no próprio arquivo) com
   o item que você adicionou e a rota da página. Se já existir uma entrada
   pra data de hoje (de uma rodada anterior no mesmo dia), acrescente o item
   nela em vez de criar uma segunda entrada pro mesmo dia.
2. Faça um commit git local (`git add -A && git commit -m "..."`) resumindo
   o que mudou. Não precisa (e não tem como) dar push — não há remote com
   credenciais configuradas pro seu usuário, o commit é só pra manter
   histórico local navegável.

## Se algo der errado
Se o build falhar e você não conseguir corrigir, ou se ficar em dúvida se
uma ação sairia do escopo de `/home/devtools-bot/devtools`, prefira não subir nada nessa
rodada a arriscar quebrar o que já está no ar. O site em produção
continuar como está é sempre preferível a subir algo quebrado. Rodada sem
nenhuma mudança é um resultado válido e esperado.

**Se você decidiu não dar commit, desfaça suas próprias mudanças antes de
terminar** (`git checkout -- .` pros arquivos que você editou e `rm` nos
arquivos novos que você criou) — deixe o working tree limpo, do jeito que
encontrou. Já aconteceu de uma rodada quebrada deixar arquivo pela metade
pra trás sem reverter, e isso confunde a rodada seguinte (que vê mudança
não commitada sem saber se é dela ou de outra rodada).
